# LocaleLens — contributor notes
- Package manager: **bun** (`bun install`, `bun run test`, `bun run build`). Node >=22.18 for runtime.
- Packages import each other as `@localelens/<name>` (tsconfig paths + vitest alias → `src/index.ts`).
- Never accept filesystem paths from the browser. Files are addressed by opaque ids (`fileId`, `workspaceId`).
- Source edits: magic-string on Babel node ranges (no regex, no regenerate).
- Status truth lives in docs/STATUS.md. Do not claim a feature there unless a test exercises it.
- CLI tests spawn `packages/cli/dist/bin.js`: run `bun run build` before `vitest` after CLI changes.
- Config provenance (`configDefs` in ast-engine/candidates.ts): same-file at enumerate time; otherwise the agent searches other source files by property name and keeps only definitions whose value matches the on-screen text (`crossFileDefs`). Import graphs are never followed.
- Release (see docs/RELEASING.md): CI creates the GitHub Release only (tag, zips, checksums); npm publishing is done by hand from the tarballs, so published packages have no `publishConfig`. Publishable: `localelens` (the CLI), `@localelens/vite`, `@localelens/next`; all other packages stay `private: true`.
- Versions: Changesets (fixed group of the 3 packages) then `scripts/sync-versions.mjs` syncs `manifest.json` and both `VERSION` constants to the CLI version (private packages are not bumped: the Changesets action reads a CHANGELOG.md for each changed package.json). Never hand-edit versions; `release-check` fails on drift.
- Never add example/, .keys/, .env, session.json to git or release assets (allowlists in `release-check.mjs` / `release-artifacts.mjs`). `example/` is gitignored; do not read or search it.
- Workflows pin actions by commit SHA; `ci.yml` runs on PRs and via `release.yml` for `main`. Workflows have not run on GitHub yet.
